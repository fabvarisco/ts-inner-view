1 Contextualização e diagnóstico

1.1 O projeto e a forma atual de trabalho

O Inner View, trabalho final da pós-graduação do grupo, é uma plataforma de tours virtuais imobiliários: o corretor cadastra o imóvel, envia as fotos panorâmicas de cada ambiente, liga um ambiente ao outro por pontos de navegação e publica um tour que o cliente percorre à distância. São duas aplicações no mesmo repositório: a API server-api (NestJS, TypeScript, Prisma, PostgreSQL, autenticação por JWT, 26 rotas e 12 modelos de dados) e o aplicativo inner-view-client (Angular, Ionic, Capacitor para Android, Three.js no visualizador 360°). O ambiente local já está descrito em código, com Dockerfile e docker-compose.yml.

A forma de trabalho aparece no histórico do Git: 19 commits entre 09/06/2026 e 26/09/2026, uma única branch (main) e nenhum pull request. Todos comitam direto na main, sem revisão. O diretório .github/ não existia, ou seja, não havia nenhuma automação. Cada integrante sobe o banco, roda o projeto e testa na própria máquina — o que funciona, funciona só ali.

2 O desenho do pipeline de CI/CD

2.1 Da cultura ao desenho: Três Caminhos e CALMS

No Inner View não existe o muro entre desenvolvimento e operação de O Projeto Fênix: existe ausência de operação, porque não há o que operar fora do localhost. Os sintomas, porém, são os mesmos dos Três Caminhos: falta fluxo (o trabalho não chega ao usuário), falta feedback (os três testes quebrados provam) e falta aprendizado contínuo (nada é medido). A esteira responde aos três: entregas pequenas e um único artefato promovido criam o fluxo; lint, testes e verificações de segurança respondem em minutos no próprio pull request; e as métricas da seção 4 fecham o aprendizado.

Usamos o modelo CALMS como lista de conferência, para a proposta não virar só automação. Cultura: a main passa a ser responsabilidade de todos — esteira vermelha vira prioridade do grupo, e falha vira análise sem procurar culpado. Automação: quatro workflows cobrindo lint, build, teste, segurança e deploy, onde hoje não há nada. Lean: branches de até dois dias e pull requests pequenos, no lugar de entregas grandes que nunca chegam ao usuário. Medição: as nove métricas da seção 4, coletadas pela própria esteira. Compartilhamento: revisão por outro integrante e rodízio de quem publica a release, para o conhecimento não ficar com uma pessoa só.

2.2 Branches, ambientes e critérios de promoção

A estratégia escolhida é trunk-based development: a main fica sempre pronta para entregar, e cada tarefa vive em uma branch curta (feat/, fix/) de no máximo dois dias, que volta para a main por pull request. Descartamos o GitFlow porque, para quatro pessoas e entregas pequenas, as branches extras só atrasariam o feedback. A main fica protegida no GitHub: sem pull request aprovado por um colega e sem a esteira verde, não entra nada.

Quadro 2 — Ambientes e critérios de promoção. Fonte: elaborado pelos autores.

A API não aparece no quadro como ambiente porque ainda não tem host contratado. O que a esteira já faz por ela é empacotar: cada merge gera a imagem, ela passa pelo scan e é publicada no GHCR identificada pelo SHA do commit. Quando houver host, o artefato já existe, versionado e com inventário — falta apenas o passo que o coloca no ar.

Duas decisões sustentam o desenho. A primeira: o artefato é construído uma vez só, no merge em main, e daí em diante apenas promovido — o que chega à produção é exatamente o que foi testado. Na Vercel isso tem tradução direta: o merge roda vercel deploy --prebuilt --prod --skip-domain, que cria um deployment de produção com URL própria mas sem apontar o domínio para ele; a promoção, na tag, é um vercel promote que apenas move o domínio para esse mesmo deployment. A segunda: a tag no Git é o gatilho da produção, de modo que o grupo decide quando liberar sem perder a automação do caminho. Como todo deployment anterior continua existindo e imutável, voltar atrás é mover o ponteiro de volta.

2.5 Implantação e consistência entre ambientes

A unidade de entrega do aplicativo é o deployment imutável da Vercel. Uma vez criado, ele não muda: recebe uma URL própria, derivada do build, e continua existindo mesmo depois de substituído. "Publicar" e "voltar atrás" deixam de ser operações de infraestrutura e viram a mesma operação — apontar o domínio para um deployment que já existe. É o que o vercel promote faz na tag e o vercel rollback faz quando o health check de produção reprova, sem novo build e sem janela de indisponibilidade. O efeito prático é o mesmo que se buscaria com blue-green, só que sem manter duas infraestruturas de pé: a versão nova é validada em uma URL real antes de receber o domínio.

Para a API, a unidade continua sendo o contêiner: o mesmo Dockerfile multi-estágio gera a imagem que será usada em qualquer ambiente, o que elimina o clássico "funcionava em homologação". Como as migrations rodam ao subir o contêiner e, em uma troca de versão, duas convivem por instantes, toda migration precisa ser compatível com a versão anterior — adicionar coluna em vez de renomear, e remover só na entrega seguinte. Essa regra vale desde já, mesmo antes de existir host, porque é uma disciplina de como escrever a migration e não de como fazer o deploy.

Duas limitações deste desenho ficam registradas, porque ignorá-las seria vender uma esteira melhor do que ela é:

  • Homologação e produção compartilham a configuração. Construir uma vez só e promover o mesmo artefato tem um custo: em uma aplicação Angular a configuração entra no bundle durante o build, então o deployment validado em homologação já carrega as variáveis de produção. Hoje isso é inofensivo, porque a API não está no ar; quando estiver, ou se abre mão de promover o mesmo artefato — construindo duas vezes —, ou se passa a ler a configuração em tempo de execução, carregando um config.json servido pelo ambiente antes de a aplicação iniciar. O grupo prefere o segundo caminho, e ele está na fase 3 do plano.
  • O canary fica para depois. Liberar para uma fração dos usuários só faz sentido com usuários reais e com monitoramento que mostre a diferença entre as duas fatias. Sem rota de saúde e sem log organizado, um canary daria a sensação de cuidado sem a informação que o justifica.

3 Controles de segurança integrados à esteira

A regra que organiza os gates é simples: bloqueia o que dá para resolver agora, avisa o resto. Um gate que reprova por algo que o grupo não tem como corrigir ensina o time a ignorar a esteira — e esteira ignorada é pior do que nenhuma, porque dá falsa sensação de segurança.

Quatro escolhas merecem registro, porque é nelas que a esteira encosta na realidade do projeto:

  • O problema antigo avisa; o problema novo bloqueia. As 89 falhas de lint, os 3 testes quebrados e as vulnerabilidades que já existiam entram como aviso, marcadas com TODO nos workflows. Se entrassem como bloqueio, a main nasceria vermelha e o grupo se acostumaria a ignorar o alerta. Cada TODO tem prazo na fase 1 do plano da seção 5.
  • Segredo é a exceção. Segredo vazado não tem conserto depois: precisa ser trocado. Por isso esse gate bloqueia desde o primeiro dia, e o segredo reserva ?? 'access-secret' será trocado por um erro na inicialização — sem a variável, a API não sobe, em vez de subir insegura.
  • Cada ambiente guarda os próprios segredos. Os segredos de produção ficam nos environments do GitHub e só são acessíveis ao deploy aprovado; a configuração da aplicação (o API_URL) fica nas variáveis do projeto na Vercel, separada por environment; e o .env.example passa a ter marcadores em vez de valores que parecem reais. A esteira precisa de três segredos para publicar — VERCEL_TOKEN, VERCEL_ORG_ID e VERCEL_PROJECT_ID — e de nenhuma credencial de servidor, porque não há servidor.
  • Desligamos o deploy automático da Vercel. Por padrão a Vercel publica sozinha a cada push, o que colocaria o deploy ao lado dos gates em vez de depois deles: o código iria ao ar enquanto o SAST ainda roda. Em vercel.json a integração Git foi desativada ("github": { "enabled": false }) e quem publica é o workflow, pela CLI. Perde-se um pouco de comodidade e ganha-se a única coisa que faz um gate ser gate: a capacidade de impedir.

5 Plano de adoção e considerações finais

A adoção é dividida em três fases, para o grupo não tentar ligar tudo de uma vez. Fase 1 (semanas 1 e 2): ligar o CI e o secrets scanning, proteger a main exigindo pull request revisado, e limpar a dívida que hoje só gera aviso — corrigir os 3 testes do aplicativo, as 89 falhas de lint e o segredo reserva no código. Fase 2 (semanas 3 e 4): cadastrar os três segredos da Vercel, tornar SAST, SCA e SBOM obrigatórios, ligar o Dependabot, exigir 50% de cobertura e fazer o primeiro deploy automático em homologação — o primeiro da história do projeto. Fase 3 (semanas 5 a 8): DAST em homologação, produção por tag com aprovação e rollback por promoção, leitura da configuração em tempo de execução para separar de fato homologação de produção, ajustes de segurança da API (CORS, cabeçalhos, limite de requisições, contêiner sem root, Swagger fechado em produção), definição do host da API e o monitoramento mínimo que torna MTTD e MTTR mensuráveis.

O trabalho mostrou que aplicar DevSecOps a um projeto real depende menos de escolher ferramentas — as que usamos são gratuitas e padrão de mercado — e mais de aceitar um diagnóstico desconfortável. O Inner View tem testes em TDD, arquitetura organizada e Docker bem feito e, ao mesmo tempo, tinha três testes quebrados na branch principal, um segredo escrito no código de autenticação e nenhum ambiente além da máquina de cada integrante. É o que acontece quando a qualidade depende da disciplina de cada um em vez de estar automatizada na esteira. A proposta ataca essa lacuna: devolve resposta rápida ao grupo, coloca a segurança no mesmo pull request que o teste em vez de num portão final, separa o que bloqueia do que só avisa e torna o caminho até a produção repetível. A escolha da Vercel para hospedar o aplicativo fechou a última pendência do desenho anterior: o destino existe, o deploy é executado pela esteira e o rollback é um comando, de modo que o único passo ainda no papel é o host da API. Todo o restante está versionado no repositório e reproduzido nos anexos.

#
# O client (Angular/Ionic) é publicado na Vercel; a API é empacotada como imagem
# versionada no GHCR. A integração Git da Vercel está desligada em vercel.json
# (`"github": { "enabled": false }`): quem publica é esta esteira, para que os
# gates de segurança aconteçam ANTES do deploy e não em paralelo a ele.
#
# Gates cobertos aqui: 3 (empacotamento), 4 (homologação), 5 (DAST) e 6 (produção).
#
# O artefato é construído UMA VEZ, no merge em main, e promovido:
#   vercel build --prod  →  vercel deploy --prebuilt --prod --skip-domain  →  vercel promote
# O `--skip-domain` cria um deployment de produção que ainda NÃO recebe o domínio.
# Ele é validado em homologação (smoke + DAST) e, na tag, o `promote` apenas aponta
# o domínio para esse mesmo deployment — o que vai ao ar é exatamente o que foi testado.
#
# Secrets necessários no repositório:
#   VERCEL_TOKEN      token de acesso da Vercel
#   VERCEL_ORG_ID     id da conta/time  (vercel.json local: .vercel/project.json)
#   VERCEL_PROJECT_ID id do projeto do client na Vercel
# Secret opcional:
#   VERCEL_AUTOMATION_BYPASS_SECRET  libera smoke test e DAST quando o projeto usa
#                                    Deployment Protection (Vercel > Settings > Protection)
# Variáveis (Settings > Variables):
#   PRODUCTION_URL    obrigatória para a promoção: domínio de produção do projeto
#   STAGING_ALIAS     opcional: domínio fixo de homologação, para não caçar o link
name: CD

concurrency:
  group: cd-${{ github.ref }}
  cancel-in-progress: false

permissions:
  contents: read
  packages: write

env:
  CLIENT_DIR: inner-view-client
  IMAGE: ghcr.io/${{ github.repository }}/server-api
  VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
  VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}

      # Falhar aqui é melhor do que promover e descobrir depois que o health
      # check testou uma URL vazia.
      - name: Conferir a configuração
        run: |
          if [ -z '${{ vars.PRODUCTION_URL }}' ]; then
            echo "::error::Defina a variável PRODUCTION_URL (Settings > Variables) com o domínio de produção."
            exit 1
          fi

        run: npm install --global vercel@60

      # Vincula o diretório ao projeto a partir de VERCEL_ORG_ID/VERCEL_PROJECT_ID,
      # para que `promote` e `rollback` saibam sobre qual projeto agir.
      - name: Vincular o projeto
        run: vercel pull --yes --environment=production --token='${{ secrets.VERCEL_TOKEN }}'

      # Se a tag apontar para um commit que nunca passou por homologação, não há
      # o que promover — e a esteira reprova em vez de construir algo novo.
      - id: find
        name: Localizar o deployment validado em homologação
        env:
          TOKEN: ${{ secrets.VERCEL_TOKEN }}
        run: |
          set -euo pipefail
          query="projectId=$VERCEL_PROJECT_ID&meta-githubCommitSha=$GITHUB_SHA&state=READY&target=production&limit=1"
          case "$VERCEL_ORG_ID" in team_*) query="$query&teamId=$VERCEL_ORG_ID" ;; esac
          resp=$(curl -fsS -H "Authorization: Bearer $TOKEN" "https://api.vercel.com/v6/deployments?$query")
          url=$(echo "$resp" | jq -r '.deployments[0].url // empty')
          if [ -z "$url" ]; then
            echo "::error::Nenhum deployment pronto para o commit $GITHUB_SHA."
            echo "::error::Marque com tag apenas commits que já passaram por homologação."
            exit 1
          fi
          echo "url=https://$url" >> "$GITHUB_OUTPUT"

      # Qual deployment o domínio de produção serve NESTE momento. É para ele que
      # o rollback volta, e por isso a consulta é no projeto e não na lista de
      # deployments (o mais recente da lista é justamente o que vamos promover).
      - name: Guardar a produção atual (para rollback)
        id: current
        env:
          TOKEN: ${{ secrets.VERCEL_TOKEN }}
        run: |
          set -euo pipefail
          query=""
          case "$VERCEL_ORG_ID" in team_*) query="?teamId=$VERCEL_ORG_ID" ;; esac
          resp=$(curl -fsS -H "Authorization: Bearer $TOKEN" \
            "https://api.vercel.com/v9/projects/$VERCEL_PROJECT_ID$query")
          echo "url=$(echo "$resp" | jq -r '.targets.production.url // empty')" >> "$GITHUB_OUTPUT"

      # Promoção: o domínio de produção passa a apontar para o deployment validado.
      - name: Promover ${{ github.ref_name }}
        run: |
          vercel promote '${{ steps.find.outputs.url }}' --token='${{ secrets.VERCEL_TOKEN }}'
          echo "### Produção: ${{ github.ref_name }} → ${{ steps.find.outputs.url }}" >> "$GITHUB_STEP_SUMMARY"

      - name: Health check em produção
        run: |
          curl -fsS --retry 5 --retry-delay 5 --retry-all-errors '${{ vars.PRODUCTION_URL }}' | grep -q '<app-root'
          echo "Health check OK"

      # Rollback: volta o domínio para o deployment anterior, que continua existindo.
      # Na Vercel o deployment é imutável, então desfazer é trocar o ponteiro.
      - name: Rollback automático em caso de falha
        if: failure() && steps.current.outputs.url != ''
        run: |
          vercel rollback 'https://${{ steps.current.outputs.url }}' --token='${{ secrets.VERCEL_TOKEN }}'
          echo "::warning::Produção revertida para https://${{ steps.current.outputs.url }}"

inner-view-client/scripts/set-api-url.mjs — substitui o endereço da API no bundle a partir da variável do ambiente. Sem a variável, o build falha.

// Injeta a URL da API no bundle de produção a partir da variável de ambiente
// API_URL, definida no projeto da Vercel (uma por environment: Preview e Production).
//
// Motivo: o endereço da API é configuração de ambiente, não código. Antes desta
// esteira o valor estava fixo em environment.prod.ts (`https://api.seudominio.com`),
// um endereço que não existe — o build passava e a aplicação publicada quebrava.
//
// O script falha quando API_URL não está definida, pela mesma regra aplicada ao
// segredo do JWT na API: sem a configuração, a aplicação não sobe em vez de subir
// apontando para lugar nenhum.

import { readFileSync, writeFileSync } from 'node:fs';

const target = new URL('../src/environments/environment.prod.ts', import.meta.url);
const apiUrl = (process.env.API_URL ?? '').trim();

if (!apiUrl) {
  console.error(
    '[set-api-url] API_URL não está definida.\n' +
      '              Configure a variável no projeto da Vercel (Settings > Environment Variables)\n' +
      '              ou exporte API_URL antes de rodar o build.'
  );
  process.exit(1);
}

if (!/^(https:\/\/|\/)/.test(apiUrl)) {
  console.error(`[set-api-url] API_URL inválida: "${apiUrl}". Use https:// ou um caminho iniciado por /.`);
  process.exit(1);
}

const source = readFileSync(target, 'utf8');
const patched = source.replace(/apiUrl:\s*'[^']*'/, `apiUrl: '${apiUrl.replace(/\/+$/, '')}'`);

if (patched === source) {
  console.error('[set-api-url] Não encontrei a chave apiUrl em environment.prod.ts. Build interrompido.');
  process.exit(1);
}

writeFileSync(target, patched);
console.log(`[set-api-url] apiUrl = ${apiUrl}`);

# Regras do ZAP Baseline sobre o client publicado em homologação na Vercel.
# WARN = alerta, não bloqueia. FAIL = bloqueia a promoção para produção.
