Contextualização

Tour virtual, duas aplicações, uma main

Objetivo

Visitar o imóvel sem ir até lá

O corretor cadastra o imóvel, envia o panorama de cada cômodo, liga um ambiente ao outro e publica o tour.

server-api

NestJS, Prisma, PostgreSQL

JWT, validação com Zod e Docker Compose no dia a dia. A imagem de produção é Node 22. O Swagger fica em /docs.

inner-view-client

Angular, Ionic, Three.js

O visualizador 360° roda no browser. Capacitor cobre o Android. Em produção o destino previsto é a Vercel.

Forma de trabalho observada

Cada um sobe o banco na própria máquina

19 commits entre 09/06/2026 e 26/09/2026, todos direto em main. Nenhum pull request, nenhum merge, nenhuma revisão por outro integrante.

O que o repositório passa a exigir

Trunk-based, branch curta, pull request

feat/ e fix/ voltam para main por PR. Os workflows disparam nesse PR, no push em main e na tag v*.

Diagnóstico · antes da esteira passar a valer

Integração, teste, entrega, segurança

Como o código é integrado

A main aceita qualquer push

Sem proteção de branch e sem verificação automática. O que entra em main entra porque alguém commitou, não porque um gate passou.

Como é testado

52 testes verdes, cobertura de 28%

A suíte de tours virtuais passa. O resto da API — autenticação, imóveis, usuários, panoramas — fica de fora. No client, 3 dos 5 specs quebram por falta de HttpClient e permanecem assim na main.

Como chega ao ambiente

Não chega

Em três meses e meio o software só rodou em localhost. O build de produção do client apontava para https://api.seudominio.com, um endereço que não existe. A imagem da API era gerada na máquina de quem desenvolvia e não ia para registry.

Quais verificações de segurança existem

Nenhuma automática

O .env está no .gitignore. O código de autenticação ainda assina o token com 'access-secret' se JWT_ACCESS_SECRET faltar. Dependências: 136 alertas altos na API; 1 crítico e 35 altos no client. Sem SBOM e sem varredura de segredos no histórico.

O retrato cabe numa frase: três testes do client quebrados na branch principal, sem ninguém perceber. Falta o mecanismo que avisa o grupo, não só cuidado individual.

Diagnóstico · o que mudou no repositório

A esteira existe. Parte da dívida continua aviso

Versionado

Quatro workflows e o Dependabot

ci.yml, security.yml, codeql.yml e cd.yml. A Vercel deixa de publicar sozinha: github.enabled está false.

O job da API falha se o teste quebrar

yarn test:cov roda sem continue-on-error. Build da API e build de produção do client também.

Aviso, com TODO de fase 1

Lint da API (89 erros), lint do client (1 erro), os 3 specs quebrados e o piso de 50% de cobertura seguem com continue-on-error: true. Um PR vermelho nesses passos ainda fica verde para o GitHub.

Fora do que o YAML consegue impor

Exigir revisor na main e exigir estes checks antes do merge é configuração do GitHub. Ela não está no repositório. Sem ela, o desenho de PR é convenção do grupo.

Desenho · GitHub Actions

Seis momentos, do commit à tag

  1. 01

    Estação

    Branch curta. O desenho prevê Gitleaks, ESLint e o teste do módulo tocado antes do push.

  2. 02

    Pull request para main

    CI, CodeQL, Gitleaks, Trivy e SBOM. O client ganha um preview efêmero na Vercel.

  3. 03

    Merge em main

    Um build só: vercel build --prod. A API vira imagem ghcr.io com a tag do SHA.

  4. 04

    Homologação

    vercel deploy --prebuilt --prod --skip-domain. O domínio público não se move. O smoke procura <app-root.

  5. 05

    DAST

    OWASP ZAP baseline na URL de homologação. Alerta High reprova o job. Medium e Low avisam.

  6. 06

    Tag v*

    vercel promote aponta o domínio para o mesmo deployment. Health check falho dispara vercel rollback.

A API para no passo 03: a imagem só entra no GHCR depois do scan. Ainda não há host para colocá-la no ar.

Branches, ambientes, promoção

O que foi testado é o que vai ao ar

Por que trunk-based

Quatro pessoas e entrega pequena. GitFlow acrescentaria branches de release sem ganho de feedback. A main fica sempre no estado que se pretende promover.

Por que a Vercel não publica no push

Com a integração Git ligada, o client iria ao ar enquanto o SAST ainda corre. Quem publica é o cd.yml, depois do build único.

Justificativa

O que já está no GitHub, de graça

GitHub Actions

O repositório já está no GitHub. Jenkins seria um servidor a mais para quatro pessoas.

Gitleaks

Lê o histórico inteiro. Um segredo apagado no último commit continua visível nos anteriores.

CodeQL

SAST de TypeScript no próprio GitHub. O pacote security-extended cobre injeção, cripto fraca e segredo no código.

Trivy

Uma ferramenta nas dependências e na imagem. ignore-unfixed só barra CVE que já tem correção.

Syft

SBOM CycloneDX. Responde se uma versão liberada contém a biblioteca de uma CVE nova.

OWASP ZAP

DAST passivo na URL exata de homologação. Enxerga cabeçalho ausente, o que o SAST não vê.

Dependabot

PR semanal de npm na API e no client, mensal nas Actions, semanal na imagem Docker.

Vercel

Deployment imutável, preview por PR, promoção e rollback sem segundo build.

GHCR

A imagem da API fica no registry do GitHub, marcada pelo SHA, enquanto não há host.

Jest e Karma

Já usados no projeto, inclusive nos 52 testes do módulo de tours. A esteira só passa a rodá-los.

Validação · o YAML contra o desenho

Seis pontos o workflow ainda não segura

01 · CI permissivo

Lint, client e cobertura

Três passos de ci.yml têm continue-on-error: true. O teste da API, o build e o scan de dependências seguem capazes de falhar o job.

02 · SAST publica

CodeQL não escolhe severidade

O workflow envia o resultado. Ele não termina com erro por alerta alto ou crítico. Esse bloqueio mora na política de code scanning do GitHub.

03 · Esteiras paralelas

O CD não espera o CI

cd.yml não declara needs de CI, Security ou CodeQL. Sem check obrigatório na branch, um merge com teste vermelho ainda publica.

04 · DAST à parte

A tag não consulta o ZAP

promote-production só procura um deployment READY daquele SHA. A tag não roda o DAST de novo, e o ZAP só enxerga o client.

05 · Gate local

Não há pre-commit

Gitleaks existe no PR, com fetch-depth: 0. Na máquina do desenvolvedor, não. O fallback 'access-secret' continua no serviço de token.

06 · SCA amplo

A pasta inteira entra no bloqueio

O critério implementado é severidade mais correção disponível. O desenho ainda pedia aviso, e não bloqueio, para devDependencies.

Validação final

O desenho atende. O bloqueio, em parte

Atende

Os quatro pontos estão no repositório

Contexto e dívida estão nos comentários do CI. O caminho do PR ao promote está no CD. SAST, DAST, SCA, SBOM e secrets têm workflow, com a regra de bloquear ou avisar escrita no passo. A tabela de métricas tem linha de base e meta.

Ainda aviso

O que o TODO deixou passar

Lint, specs do client e o piso de cobertura. O fallback do JWT. A separação entre dependência de produção e ferramenta de desenvolvimento. A coleta automática das métricas DORA.

Configuração do GitHub

O que o YAML não carrega

Proteção da main com os quatro workflows obrigatórios. Revisor no environment production. Code scanning reprovando alerta alto. Sem isso, a tag e o merge seguem possíveis com a esteira vermelha ao lado.

A API segue empacotada e sem host. O client tem destino, build único, smoke, DAST e rollback. O próximo passo que torna o gate um gate é ligar esses checks na branch, e tirar o continue-on-error da dívida já conhecida.
