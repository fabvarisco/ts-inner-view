Item 1 · Questões de projeto (Coulouris et al.)

Cada desafio, aplicado ao Inner View

Heterogeneidade

Navegador, app Ionic e Node trocam HTTP com JSON. Nenhum dos lados depende da linguagem ou do sistema operacional do outro.

Abertura

A interface REST está publicada no Swagger (/docs), e qualquer cliente novo consegue integrar a partir dela.

Segurança

JWT de acesso (1 dia) e de refresh (7 dias), guards por papel e Zod validando toda entrada. Em produção, tudo passa por HTTPS.

Escalabilidade

A API não guarda sessão, então é possível subir N réplicas atrás de um balanceador. O estado fica todo no PostgreSQL.

Tratamento de falhas

Healthcheck do banco, restart: unless-stopped e transações: se uma escrita falha no meio, nada fica pela metade.

Concorrência

Dois corretores podem editar o mesmo tour ao mesmo tempo. Essa é a região crítica que o lock distribuído protege.

Transparência

O proxy /api esconde onde a API roda (localização), e o balanceador esconde quantas réplicas existem (replicação).

Qualidade de serviço

Os panoramas viajam em base64. O limite do corpo JSON foi ampliado para 50 MB em main.ts.

Item 1 · Arquitetura

Cliente-servidor em três camadas

Por que cliente-servidor

  • Uma fonte de verdade. O tour, os panoramas e os hotspots de cada imobiliária precisam estar consistentes para todos os visitantes.
  • Autorização central. Só o servidor confere o JWT e o agencyId. Num P2P, cada par teria que confiar nos outros.
  • Clientes efêmeros. O visitante abre o link, navega e fecha. Não há pares estáveis para guardar nem repassar os dados.
  • Escala horizontal simples. A API é stateless, então basta adicionar réplicas.

Por que não peer-to-peer

O P2P compensa quando os recursos estão espalhados entre os usuários. Aqui, eles pertencem à imobiliária.

Padrão Broker (Microsoft p&p)

O cliente não conhece quem atende

O NestJS funciona como o middleware do broker. Ele recebe a requisição, localiza o controller pela rota, aplica guards e pipes e chama o service. Do lado do cliente, o HttpClient do Angular é o proxy: esconde a serialização e o transporte.

Por que JSON

  • Nativo nos dois lados. TypeScript no cliente e no servidor, sem gerar stubs.
  • Legível e documentado. O Swagger mostra o formato exato e dá para testar com curl.
  • Validação explícita. O Zod garante o tipo na chegada, coisa que o JSON sozinho não faz.

Por que não Protobuf / gRPC

Ganharíamos alguns bytes, mas o navegador perderia o suporte direto e o contrato deixaria de ser legível. Nessa escala, a conta não fecha.

Item 1 · Paradigma de comunicação

Invocação remota por requisição-resposta

ParadigmaComo seria no Inner ViewDecisão
Requisição-resposta (REST/HTTP) O cliente envia a operação e espera o resultado: criar o tour, editar um panorama, listar imóveis. Adotado. Toda operação do corretor precisa de confirmação imediata (200, 400, 409). O HTTP é stateless e passa por proxy e balanceador sem esforço.
RPC / RMI Stubs gerados (gRPC, Java RMI) chamando métodos remotos. Não. O navegador não fala gRPC nativo, e o RMI amarra tudo ao Java. O REST já entrega a mesma semântica.
Publicação-assinatura Cada visualização do tour vira um evento, e a analytics assina. Evolução futura. Hoje o volume é baixo e a gravação síncrona dá conta.
Fila de mensagens Processar os panoramas grandes (gerar miniatura) fora da requisição. Evolução futura, se o upload passar a demorar.
Comunicação em grupo / memória compartilhada Réplicas sincronizando estado entre si. Não. As réplicas não guardam estado, e o PostgreSQL faz o papel de memória compartilhada.

Item 1 · Exclusão mútua · o problema

Dois corretores, o mesmo tour, duas réplicas

Região crítica

A atualização do tour e dos seus panoramas

  • Atualização perdida. As duas réplicas leem o mesmo estado, e a última escrita apaga a anterior.
  • Inconsistência. Um corretor apaga o panorama da cozinha enquanto o outro cria um hotspot que aponta para ele.
  • Lock em memória não resolve. Um mutex no Node só vale dentro de um processo, e a réplica #2 não fica sabendo dele.

Requisitos (Coulouris, cap. 15)

EM1 segurança: no máximo um processo por vez na região. EM2 vivacidade: todo pedido acaba sendo atendido ou recusado. Não pode haver deadlock nem lock órfão.

Item 1 · Exclusão mútua · a solução

Servidor central: o PostgreSQL coordena o lock

Algoritmo

pg_try_advisory_xact_lock

Cada tour vira uma chave inteira (hashtext(tourId)). A réplica abre uma transação e pede o lock ao banco. Quem consegue edita. Quem não consegue recebe 409 Conflict e tenta de novo depois.

  • Segurança. O banco é o único coordenador, então nunca há dois donos ao mesmo tempo.
  • Sem lock órfão. O lock pertence à transação. Se a réplica cai, a conexão fecha e o banco libera o lock.
  • Sem deadlock. O try não bloqueia: responde na hora.
  • Granular. Um lock por tour, então edições em tours diferentes seguem em paralelo.

Por que não Ricart-Agrawala ou anel

Os dois exigem que as réplicas se conheçam e troquem mensagens entre si. As nossas sobem e caem a todo momento e já compartilham o PostgreSQL, que é o coordenador natural. O ponto único de falha já existe, porque sem banco não há edição de qualquer forma.

Item 2 · Implementação

O lock dentro do caso de uso

server-api/src/modules/virtual-tours/services/update-virtual-tour.service.ts

async execute(id, dto, currentUser) {
  // Região crítica: tudo dentro de uma transação.
  return this.prisma.$transaction(async (tx) => {
    // Pede o lock ao PostgreSQL (coordenador central).
    // Não bloqueia: devolve true/false na hora.
    const [{ locked }] = await tx.$queryRaw`
      SELECT pg_try_advisory_xact_lock(hashtext(${id})) AS locked`;

    // Outra réplica está editando este tour.
    if (!locked) throw new ConflictException(
      'Tour em edição por outro usuário');

    const tour = await tx.virtualTour.findFirst({
      where: { id, property: { agencyId: currentUser.agencyId } },
    });
    if (!tour) throw new NotFoundException('Virtual tour not found');

    return tx.virtualTour.update({ where: { id }, data: dto });
  }); // COMMIT ou ROLLBACK liberam o lock
}

Onde entra

No service, não no controller

O controller continua só repassando a chamada. O lock é regra do caso de uso e pode ser testado com o dublê do Prisma, como o resto da suíte.

Contrato HTTP

PATCH /virtual-tours/:id

200 editou · 409 outro corretor está editando · 404 não é da sua imobiliária · 400 corpo inválido (Zod).

Por que xact e não session lock

A liberação é automática

O Prisma usa um pool de conexões. Um lock de sessão poderia ficar preso numa conexão reaproveitada. O de transação morre com o COMMIT.

  | jq -r .accessToken)

# 3. edições simultâneas, uma em cada réplica
for p in 3000 3001; do
  curl -s -o /dev/null -w "$p → %{http_code}\n" -X PATCH \
    localhost:$p/virtual-tours/$TOUR \
    -H "Authorization: Bearer $TOKEN" \
    -H 'Content-Type: application/json' \
    -d '{"status":"PUBLISHED"}' &
done; wait

Resultado esperado

200 e 409

Uma requisição entra na região crítica. A outra é recusada enquanto o lock está com a primeira.
